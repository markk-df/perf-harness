# perf-harness

[![Open in GitHub Codespaces](https://github.com/codespaces/badge.svg)](https://codespaces.new/markk-df/perf-harness)

> **Note:** This entire repository, including all of its code, scripts, and documentation, was generated by AI.

A manifest-driven benchmark harness for comparing the performance of one git branch against another.

You describe *what to build*, *what to run*, and *how to measure* in a single JSON file. The harness
then builds each branch in its own worktree, runs your workload under a profiler (or a plain timer),
checks that the output is still correct, and reports the difference between branches on the metric
you care about. It is not tied to any one project: anything that builds from a git branch and emits a
profiler trace can be measured.

## Why this exists

The usual question is: *"Did this change actually make things faster, and by how much?"* Wall-clock
time alone answers that badly. Modern CPUs change frequency under load, so the same code can take a
different number of seconds from one run to the next. This harness measures **frequency-invariant**
metrics instead -- for example allocated bytes or retired instructions pulled from an ETW trace -- so
the number reflects the code, not the moment you happened to run it. Wall time is still recorded, but
normalized by the CPU frequency observed during the run.

## What makes it different from existing tools

- [`hyperfine`](https://github.com/sharkdp/hyperfine) runs any command but reports wall-clock only.
- [`asv`](https://asv.readthedocs.io/) walks git history but is built around timing Python functions.
- [`BenchmarkDotNet`](https://benchmarkdotnet.org/) emits its own ETW but locks you into its in-process harness: you cannot swap in a different profiler or trace extractor.

This harness is the intersection nobody else covers: **git-branch loop + arbitrary build/run command +
bring-your-own profiler and extractor + frequency-invariant reporting**, gated on output correctness.

## Requirements

- PowerShell 7 (`pwsh`).
- `git` 2.5+ (for worktrees).
- Whatever your manifest's build and run commands need (a compiler, a runtime, etc.).
- A profiler that writes a trace file, only if you use the `perfview` collector. The `time`
  collector needs nothing extra and is the easiest way to try the harness.
- The bundled metric extractor, if your `perfview` manifest points at it. It is
  a .NET 8 console app under [`tools/EtlPerfReport`](tools/EtlPerfReport), built with a .NET SDK (8 or newer).
  You do not build it by hand: a `perfview` manifest can build it
  in its `setup` phase on every run, so it is always current. See [`tools\README.md`](tools/README.md). The `time` and
  `demo` paths do not need it.
- Administrator rights if your profiler needs them (PerfView/ETW does), or if you let the harness
  stabilize CPU frequency (the default). The `time` collector with `-NoStabilize` needs no elevation,
  which is exactly what the demo below uses.

## Try it in one minute

The demo uses the `time` collector, so it needs no profiler and no admin rights. It creates a
throwaway repo with a slow branch and a fast branch, then measures the difference. You should see the
`faster` branch land well below `base` with a negative delta.

### In a GitHub Codespace

Click the badge above (or *Code -> Codespaces -> Create codespace*) and wait for it to build. The
container installs PowerShell and Node and runs `Setup-Demo.ps1` for you, so in the terminal you only
run the harness itself:

```powershell
pwsh -File ./Invoke-PerfHarness.ps1 -Manifest ./examples/demo.manifest.json -NoStabilize
```

### Locally

`cd` into a clone of this repo and run two lines -- first prepare the demo repo, then run the harness:

```powershell
pwsh -File ./examples/demo/Setup-Demo.ps1
pwsh -File ./Invoke-PerfHarness.ps1 -Manifest ./examples/demo.manifest.json -NoStabilize
```

### Why `-NoStabilize`

Stabilization steadies the numbers by reducing CPU-frequency noise through Windows `powercfg`, which
does not exist on Linux. A Codespace is Linux, so `-NoStabilize` is required there. On Windows you can
drop it and run from an elevated shell to get the extra frequency control.

## Run with a real profiler (perfview)

A `perfview` manifest uses the `perfview` collector, so it must run from an **elevated** PowerShell 7
(ETW needs Administrator). The harness checks this for you and stops early if it is not elevated.

A `perfview` manifest also needs the bundled extractor, but you do **not** build it by hand: list
`dotnet build tools\EtlPerfReport -c Release` in the manifest's `setup` phase and the harness rebuilds
it (an incremental no-op once it is up to date) at the start of every run. If you ever want to build it
standalone -- for example to run the extractor directly on an ETL -- the command is:

```powershell
dotnet build tools\EtlPerfReport -c Release
```

Always prove the chain before committing a long run. Make a one-comparison, one-repetition copy of your
manifest, writing to its own `results-smoke/` folder, so a single run exercises the whole pipeline --
real build, PerfView capture, oracle check, and metric extraction -- in minutes:

```powershell
cd C:\work\perf-harness
pwsh -File .\Invoke-PerfHarness.ps1 -Manifest .\your-smoke.manifest.json
```

A green smoke run means: both branches built, the workload ran under PerfView, the oracle confirmed
the output still matches, and the extractor produced a metric. Once that passes, run the full
benchmark (all comparisons, warmups, and repetitions):

```powershell
pwsh -File .\Invoke-PerfHarness.ps1 -Manifest .\your.manifest.json
```

Narrow a full run to specific comparisons with `-Only`, for example
`-Only speedup`. If a long run is interrupted, `-Resume` continues where it stopped.

Keep a `perfview` manifest small on disk: scope its `clrEvents`/`kernelEvents` to just what the metric
needs and leave `cpuCounters` off, so the trace carries no CPU-sample stacks and no PMU counters. With
`maxTraceGB`/`minFreeGB` set, a watchdog aborts any single trace whose file would exceed `maxTraceGB` on disk, or
would drop free disk space below `minFreeGB`. See "Disk safety" in the manifest reference
before turning `cpuCounters` back on. 
## Core ideas

**Variant.** One thing you want to measure, named by a git branch. The branch is expected to already
contain any profiler instrumentation, so switching branches is all it takes to test it. A variant may
also carry optional `args` appended to its workload command, so two variants can share one branch and
differ only by command line - that prices a single flag or option without a throwaway branch (see the
manifest reference).

**Workload.** One command to run (a single process invocation, no shell operators), plus optional
*seed* (state to restore before the run) and *oracle* (a check that the output is still correct).
A manifest can define several workloads, and each one must stay a single command. Do not chain
multiple commands into one workload with shell operators: running several steps in the same process
mixes their measurements and changes its GC and JIT behavior, which is often the very thing you are
trying to measure.

**Comparison.** A baseline variant versus a candidate variant on one workload. You list comparisons
explicitly, because the interesting pairs are not always "everything against a single baseline"
(for example: workstation GC vs server GC, then before-change vs after-change).

**Collector.** How a single run is measured. `perfview` wraps your command with ETW and CPU
counters; `command` runs a wrapper you supply (bring-your-own profiler) that must leave a trace at
`{trace}`; `time` just runs and times it. The collector wraps exactly one process, which is why a
workload command must be a single invocation with no shell operators.

**Extractor.** An external command you name in the manifest that turns a trace file into a small JSON
object of numbers. The harness stays out of the trace-parsing business entirely: it runs your
extractor, flattens the JSON, and lets you pick any number in it as the `primaryMetric`.

## How a run flows

1. **Build** each variant's branch in its own git worktree (once per variant). With
   `"buildMode": "switch"` the harness instead checks each branch out in the repo itself and rebuilds
   in place, so every variant shares one build-dir path (see the manifest reference).
2. **Stabilize** the CPU by disabling turbo, unless you pass `-NoStabilize`.
3. **Warm up** each distinct (variant, workload) pair `run.warmups` times (all discarded), priming JIT
   and file caches. A pair shared by two comparisons is warmed once, not once per comparison.
4. Run the measured repetitions **round-robin**: every comparison reaches rep *N* before any reaches
   rep *N+1*, and within each comparison its baseline and candidate run back-to-back (baseline,
   candidate) so any drift hits both equally. If `run.budgetHours` is set, the loop stops launching
   new cells once that wall-clock deadline passes -- so an interrupted or time-capped run leaves every
   comparison measured a comparable number of times, not the first few complete and the rest untouched.
5. Each repetition: restore the seed state, run under the collector while sampling CPU frequency,
   run the oracle, then run the extractor to pull metrics from the trace.
6. **Journal** every finished cell, so `-Resume` continues an interrupted run without repeating work.
7. **Report** the median of each arm and the percentage delta between them.

## Running overnight (a nightly run)

A "nightly run" is just a full run with two properties: it is bounded by a wall-clock **time budget**
so it finishes by morning, and it is launched so ETW collection can run unattended. Nothing about it
is project-specific — any manifest can be run this way.

**1. Set a time budget.** In the manifest's `run` block, set `budgetHours` to how long the machine is
free (e.g. `"budgetHours": 10`). The harness runs its repetitions round-robin and stops launching new
cells once the deadline passes, so the run lands near that duration with **every comparison measured a
comparable number of times** — never "the first few complete, the rest untouched". `reps` becomes an
upper bound: the budget, not the rep count, ends the night.

**2. Prove the chain first.** Before committing a night, run the smallest version of your pipeline once
to confirm build → collect → oracle → extract all work (a one-rep, one-comparison manifest).

**3. Launch it.** If your collector needs elevation (PerfView/ETW does), start it from an **elevated**
PowerShell 7. The harness disables turbo, stabilizes the machine, and restores the power settings on
the way out - even if it is interrupted (a hard kill is recovered on the next start). Per-variant
worktrees are kept for reuse (so `-SkipBuild`/`-Resume` work); pass `-CleanWorktrees` to remove them.

```powershell
pwsh -File .\Invoke-PerfHarness.ps1 -Manifest .\your.manifest.json
```

Leave it running. If the box is rebooted or the run is killed, `-Resume` picks up from the journal.

**4. In the morning, produce the report.** The night wrote `results.jsonl`; turn it into a readable
table (this runs nothing and needs no elevation):

```powershell
pwsh -File .\Invoke-PerfHarness.ps1 -Manifest .\your.manifest.json `
    -Aggregate results -Markdown last-night.md
```

**5. Build confidence over a week.** Three reps in one night share that night's conditions, so they
understate real variation. Instead of longer nights, run several nights and **pool** them. You have
two equivalent options:

- *Simplest — let them accumulate.* Run the same manifest each night; results append to the one
  `results` directory, and `-Aggregate results` pools every night automatically (provenance keeps it
  honest).
- *Keep nights separate* — point each night at its own directory (set `resultsDir` in the manifest, or
  move the folder afterwards), then pool them explicitly:

```powershell
pwsh -File .\Invoke-PerfHarness.ps1 -Manifest .\your.manifest.json `
    -Aggregate results\night1,results\night2,results\night3 -AllMetrics -Markdown week.md
```

Pooling is guarded automatically: nights built from different commits or a changed setup are refused
(the delta is withheld) rather than silently mixed. See [`docs\metrics-reference.md`](docs/metrics-reference.md) for the full
methodology and the report recipe.

## Output

Everything lands in the manifest's `resultsDir`:

- `results.jsonl` -- one self-describing record per repetition; the source of truth for reporting.
- `results.csv` -- the same core columns, flattened for a quick look in Excel.
- `progress.json` -- the resume journal.
- `harness.log` -- the full run log.
- `traces/` -- kept trace files (controlled by `run.keepTrace`).

Re-print the report from a finished run without re-measuring:

```powershell
pwsh -File .\Show-Report.ps1 -ResultsDir .\results-demo -Manifest .\examples\demo.manifest.json
```

Browse a finished run's results over HTTP (handy when the results live on a remote or headless
box -- e.g. a Kubernetes pod reached with `kubectl port-forward`):

```powershell
pwsh -File .\Serve-Results.ps1 -Root .\results-demo -Port 8080
# then open http://localhost:8080/report.md
```

`Serve-Results.ps1` is a read-only static file server: a directory index plus each file with a
sensible content type (markdown, csv, and logs render inline). It never writes or executes.

## Command-line options

| Option | Meaning |
|---|---|
| `-Manifest <path>` | The manifest to run (required). |
| `-Only <names>` | Run only the named comparisons. |
| `-Resume` | Continue an interrupted run using the journal. |
| `-SkipBuild` | Reuse existing worktree builds instead of rebuilding. |
| `-NoStabilize` | Do not touch power/turbo settings (use for a quick demo). |
| `-CleanWorktrees` | Remove the per-variant worktrees when finished. |
| `-ReportOnly` | Print the A/B report from existing results (e.g. after a hard abort) without running anything. |
| `-Aggregate <dirs>` | Pool several runs' results into one provenance-guarded report (comma-separated results directories). Runs nothing. |
| `-AllMetrics` | With `-Aggregate`, also print the full per-metric breakdown (each metric's own `n`, spread, and regime flag). |
| `-Markdown <path>` | With `-Aggregate`, also write the concise human report to a markdown file (headline `base → cand` table with arrowed deltas, plus the per-metric breakdown when `-AllMetrics` is set). |
| `-Json <path>` | With `-Aggregate`, also write the full aggregated report as JSON for tooling (exact medians, per-metric detail, commits, regime, status, oracle incidents). |

## Reading the report

- **primaryDeltaPct** -- the headline: percentage change in your chosen metric, candidate vs baseline.
  Negative means the candidate is lower (usually better).
- **wallDeltaPct** -- the same for frequency-normalized wall time, as a sanity check.
- **oracle** -- `passes/runs` for each arm. Anything less than a full pass means the output changed;
  treat that result as suspect regardless of how fast it was.

## A note on frequency

On some CPUs (for example Intel Meteor Lake) the firmware ignores OS frequency caps, so the harness
cannot pin the clock. It does the honest next-best thing: disable turbo to narrow the band, sample the
frequency during each run, and normalize wall time by it. This is also why a frequency-invariant
`primaryMetric` (allocations, instructions) is preferred over raw seconds for the headline number.
